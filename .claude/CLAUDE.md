# ForeverAddons

Native macOS add-on manager for World of Warcraft: Forever. A SwiftUI app (`App/`) and a package-manager CLI (`addonctl`, `Sources/addonctl/`) share one core library (`Sources/AddonKit/`), one install store and one metadata database.

**Start with `docs/README.md`.** It lists every doc with a one-line "read this when…". Load only the files you need.

## Documentation

- All docs live in `docs/`, organised by topic: `architecture/`, `features/`, `network/`, `performance/`, `app/`, `cli/`, `decisions/`.
- **One topic per file, about 40–150 lines.** Split a file when it grows past that. Don't create files so small that one question needs five of them.
- Every new file gets a line in `docs/README.md`.
- **Update the relevant doc in the same commit as the code change.**
- **After merging app changes into `main`, record the decisions:**
  - architecture, network and performance choices as `docs/decisions/NNNN-short-title.md` (context, decision, alternatives, consequences)
  - updated numbers in `docs/network/` and `docs/performance/`
- No READMEs in subfolders, except the decision index `docs/decisions/README.md`. The root `README.md` is the GitHub landing page and links into `docs/`.

## Build & test

- macOS 27, Xcode 27, Swift 6.4. If `xcode-select` points at the Command Line Tools, prefix commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.
- Core + CLI: `swift test`. Live GitHub tests are opt-in: `ADDONS_LIVE_TESTS=1 swift test`.
- App: `xcodebuild -project App/ForeverAddons.xcodeproj -scheme ForeverAddons -configuration Debug -destination 'platform=macOS' -derivedDataPath build/DerivedData build` (or `test`).
- The Xcode project is generated by XcodeGen. Edit `App/project.yml`, run `cd App && xcodegen generate`, and commit the result. Never hand-edit `project.pbxproj`.
- Run the app and tests before saying something works. Report failures plainly.

## Code

- Swift 6 language mode with strict concurrency, `NonisolatedNonsendingByDefault` and `InferIsolatedConformances`. The app target makes code run on the main actor by default, so off-main helpers need `nonisolated`.
- Shared state lives in actors or `Mutex`. No `NSLock`, no `@unchecked Sendable` in library code.
- **Use Apple frameworks; no new third-party dependencies.** The only ones are ZIPFoundation and swift-argument-parser. Persistence uses the system SQLite (`import SQLite3`).
- Tests use Swift Testing (`@Test`, `#expect`), not XCTest.
- Match the surrounding file's style. Comments explain *why*, not *what*.
- The app uses real data only. No mock managers or sample data in the app target.
- **Never read `@Environment(SomeObservable.self)` inside `Table` cells, context menus, `primaryAction` handlers or toolbar item views.** AppKit hosts those in separate hosting views. During row rebuilds (sorting, search, category changes) the object can be missing, and SwiftUI traps with "No Observable object of type … found". Pass the model, row state or closures in as plain properties instead.

## Network rules

Read `docs/network/` before touching anything that makes requests.

- **Local first.** Search, browse, sorting and categories read the SQLite metadata database only. Search goes to GitHub only when the local database has fewer than 3 matches (one request, result cached), or when the user explicitly asks.
- **Network happens:**
  - on first launch: catalogue, plus a seed of about 200 recent add-ons and the installed ones
  - every 2 hours: installed add-ons, plus repos that changed in the catalogue
  - when the user opens, installs or updates a specific add-on
- **Quota.** Prefer the quota-free `github.com/{owner}/{repo}/releases/latest` redirects and `raw.githubusercontent.com`. The API allows 60 calls per hour without a token, shared per IP. Keep a reserve, stop calling once the limit is hit, and store the rate-limit state.
- Cache everything, failures included (with a TTL). Use ETags. Never refetch what's stored and fresh.
- **Each kind of remote data has one owner that decides freshness.** For example, `GitHubSource.check` owns Forever support and latest tags. Callers state intent with a `CachePolicy` (`.preferStored`, `.revalidateIfStale`, `.forceRevalidate`). They never bypass the owner, keep a second cache, or pass `maxAge: 0`-style flags.
- At most 4 concurrent requests to github.com, with jitter. Honour `retry-after` and back off on 429/403.

## Performance rules

Read `docs/performance/` before changing hot paths or UI lists.

- No file, network, database, JSON, Markdown or image decoding work on the main actor.
- Batch database writes in transactions. Never write when nothing changed. Never hold a write transaction across an `await` on the network.
- Throttle progress to about 10–20 Hz. Per-row state lives in its own `@Observable` object, so a progress tick re-renders only that row.
- Sort and filter in the model, never in `body`.
- Screenshots: download once to the disk cache, decode thumbnails at display size, and decode full resolution only in the viewer.

## Safety

- Tests and manual runs must never touch the user's real WoW folder or `~/Library/Application Support/com.andrewmiotke.ForeverAddons`. Use temp directories or `ADDONS_DATA_DIR=<tmp>`.
- Profiling or smoke-test launches of the app run in the background, stay brief, and must be quit afterwards. Never quit the user's own running copy.
- Don't run privileged commands (the CLI install's admin prompt) yourself.

## Git & agents

- Working on `main` is fine for this project. Commit small and often, and push after merges are verified.
- Commit subjects: imperative, lowercase, under about 60 characters.
- **Split work into core and UI tasks.** A feature that needs new behaviour is two tasks:
  1. A **core task** (`Sources/AddonKit`, plus CLI if needed) that adds or changes behaviour behind the `AddonManaging` contract, with tests.
  2. A **UI task** (`App/`) that only presents it.

  Define the contract (protocol methods and model types) on `main` first, then run both in parallel.
- **UI must not break business logic, and vice versa:**
  - The app talks to the core only through `AddonManaging` and the public model types: no casts to `AddonManager`, no direct database or `GitHubSource` access.
  - Decisions (what's compatible, what to install, what to check, when to hit the network) live in the core. View models only map core results to display state.
  - The core has no UI concepts: no strings meant only for one screen, no SwiftUI or AppKit.
  - Each side's tests must pass without the other side changing.
- For parallel work, use agents in separate git worktrees with **disjoint file ownership**:
  1. Define shared contracts (protocols and model types) on `main` first.
  2. Merge each branch.
  3. Build and test everything.
  4. Update the docs, then push.
- Brief agents with these rules; they read this file too.
